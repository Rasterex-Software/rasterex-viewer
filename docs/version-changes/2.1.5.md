# Version 2.1.5 Change Notes

## Status

In progress

## Summary

Add a framework-independent view synchronization API for hosts with multiple Canvas viewer instances.

## Added APIs

`viewer.viewSync.configure({ groupId, instanceId, mode, timeoutMs? })`, `viewer.viewSync.apply(change, { pan?, zoom? })`, and `viewer.viewSync.on("changed" | "applied" | "failed", handler)`. Export `ViewSyncApi`, `ViewSyncMode`, `ViewSyncConfiguration`, `ViewSyncConfigured`, `ViewSyncChange`, `ViewSyncApplyOptions`, and result/event types.

## Changed APIs

None. The SDK version reported in diagnostics and viewer information changes to `2.1.5`.

## Removed APIs

None.

## Protocol Changes

No Protocol V1 envelope change. The SDK maps the Canvas broker `{ type, payload }` messages `configureViewSync`, `viewSyncConfigured`, `viewSyncChanged`, `applyViewSync`, `viewSyncApplied`, and `viewSyncFailed` from `VIEW_SYNC_REACT_HOST_INTEGRATION.md`.

## Compatibility Changes

Canvas must implement those broker messages for this API. The Canvas document does not specify a minimum Canvas version. The current broker `viewerReady` path does not expose dependable capability metadata, so this API does not gate on a `viewSync` capability. A deployment without a configuration response causes `configure()` to reject with the existing command timeout. This is an inference from the documented message flow; it is not a confirmed Canvas compatibility rule.

## Error Code Changes

No new codes. Invalid inputs and Canvas configuration failure use the existing SDK command error; configuration timeout uses `COMMAND_TIMEOUT` with `TIMEOUT_BASED` confidence; disconnect while configuring uses `VIEWER_NOT_READY`.

## Diagnostics Changes

The existing Canvas broker command and event diagnostics include the new message types.

## Framework Adapter Changes

None. React and other hosts use the core viewer API.

## Air-Gap and Security Impact

No new runtime URLs, dependencies, telemetry, or CDN usage. The existing broker validates origin and iframe source. Hosts with cross-origin Canvas should configure Canvas's documented `parentOrigin` URL parameter. Received `viewSyncChanged` payloads are checked against the configured group and instance before reaching application handlers.

## Migration Notes

After each viewer has completed `ready()` and its document has emitted `fileReady`, configure each viewer with a unique instance ID and a shared group ID. Relay `changed` events to sibling viewers using `apply()`. Use `applied` and `failed` events for outcomes. Unsubscribe and destroy viewers on host cleanup. Raw pan coordinates are suitable only when document geometry is aligned; start with `zoom` mode for differently sized drawings.

## Documentation Notes for Docs Agents

The complete two-viewer React integration guide is `docs/live-npm/view-sync/react-host.md`. Document the four modes, host-owned group routing policy, cross-origin `parentOrigin`, configuration timeout, event-driven application results, and document readiness and change handling. `configure()` assumes Canvas echoes the generated `requestId` in `viewSyncConfigured`; confirm this with Canvas before promising support on all deployments.

## Test and Verification Notes

Verified with `npm run build`, `npm run check:source-lines`, `node --test test/view-sync.test.mjs` (5 passing), and `npm run test:evaluation` (9 passing).

## Known Risks

The Canvas document does not guarantee request ID echo for configuration or define the minimum Canvas version. Canvas may omit request IDs on apply results. Sequence reset behavior across document changes remains a host responsibility.
